# Rust migration — status

Tracks `RUST_MIGRATION_PLAN.md`. The plan estimates 8–9 months with two
engineers; this records exactly how far along that road the tree is, so nobody
has to infer it from the code.

**Where we are: Phases 0-2 landed. Phase 3 is running in front of the live panel - Rust holds the certificate on the public port, serves eleven routers natively in whole or in part, and proxies the rest.**

The plan's definition of done for Phase 2 is "the current Python runs with the Rust helper in place of the bash one". That has happened, on the container installation, and it is the first point in this work where Rust is serving real requests rather than being tested beside them.

The Phase 0 go/no-go gate has been cleared. The plan is explicit that if the
Fernet spike fails and cannot be fixed, the project stops and the data-migration
design is reworked. It did not fail — **Rust decrypts ciphertext produced by the
production Python**, and so do the other three primitives.

### What the spikes actually prove

Every fixture is generated by the **real Python libraries the panel runs
today** (`tests/fixtures/generate.py`) and committed. The Rust tests in
`crates/snpanel-core/tests/python_compat.rs` consume those files. Nothing checks
Rust against Rust; that would pass while being completely wrong.

- **C3** — Rust decrypts six Python Fernet ciphertexts (empty, ASCII, UTF-8,
  block-aligned, 500-byte, a realistic DB password), and the derived key is
  byte-identical to `base64.urlsafe_b64encode(sha256(SECRET_KEY))`.
  *This is risk R1, the one that silently destroys every customer's database
  password.* It is closed.
- **C1** — Rust verifies five passlib bcrypt hashes including one at a
  non-default cost, and declines `/etc/shadow` hashes rather than mistaking
  them for bcrypt.
- **C4** — Rust verifies a `python-jose` token, keeps `token_version` and
  `role`, rejects an expired one and one signed with another key, and the
  tokens Rust mints carry the claims python-jose expects. This is what makes
  the strangler pattern (§9) possible.
- **C6** — Rust reproduces pyotp's codes at five fixed timestamps.
- **C19** — 16 vhosts, covering all four app types, every rewrite mode, WAF on
  and off, aliases, http-flood, a custom directive block and blocked bots,
  render **byte-identical** between Jinja2 and minijinja.

### The C19 golden set is stronger than the plan asks for

The plan's spike is "render `wordpress.conf.j2` and compare". The generator
instead drives the real `render_vhost`, which also rewrites the bot block,
applies manual SSL config and appends redirect vhosts. The template contexts
are *captured from that run* rather than written by hand, so they contain the
values Python computes — the flood zone name, the challenge block, the resolved
FPM socket path — which reading the templates would never have revealed.

## Beyond Phase 1: the nftables backend

§6.3 is why the renderer was built early. It is complete and verified,
though the privileged side that loads it belongs to Phase 2.

**The plan's stated reason for it is wrong, and the correction is worth
having.** The plan says `ipset` is deprecated on RHEL 10. On AlmaLinux 10.2
`ipset` is packaged and current - 7.22-13.el10_2 - along with
`ipset-service`. Checked against the distribution's own repositories, not
inferred.

What is actually missing is `iptables` itself:

| package | AlmaLinux 10.2 |
|---|---|
| `iptables` | not packaged |
| `iptables-legacy` | not packaged |
| `iptables-nft` | 1.8.11-16.el10_2 |
| `ipset`, `ipset-service` | 7.22-13.el10_2 |
| `nftables` | 1.1.5-6.el10_2 |
| `firewalld` | 2.4.3-4.el10_2 |

`dnf install iptables` resolves to `iptables-nft`, which installs
`/usr/sbin/iptables` as a symlink to `xtables-nft-multi` and reports
`iptables v1.8.11 (nf_tables)` - a translation shim over nftables, with no
legacy backend underneath it.

So the iptables+ipset implementation would probably *run* on AlmaLinux 10,
through the shim. Building the native backend is still the right call - a
shim is a compatibility layer with its own edges, and the panel would be
generating iptables syntax for a kernel that only speaks nftables - but it is
a different argument from "the tools are gone", and the plan should be read
with that in mind.

Verified on this machine, not merely unit-tested:

1. `nft --check` accepts the generated ruleset.
2. Loaded into an isolated network namespace, the kernel holds every rule in
   the intended order.
3. Real traffic over a veth pair produced the right verdict on four ports:
   an explicitly opened port reachable, a protected port reachable, a
   port-scoped deny blocked, and an unlisted port blocked by the final drop.

Three omissions in the plan's sample ruleset were caught by diffing it against
`firewall_apply_family` in the bash — see IMPROVEMENTS.md D1.

### Porting a router in part, by method

`users` was the first router that could not move whole, and the reason
generalises: five of its endpoints create Linux accounts, drop databases,
delete vhosts, release certificates and rewrite nginx. Half-porting one would
leave a customer row in the database with no Linux user behind it - an account
that looks right in the panel and whose website can never be uploaded to.

So a partially-ported path registers the methods it serves and falls through to
Python **by method**: `GET /api/users` is answered here, `POST /api/users` is
proxied. Without that, axum answers 405 and the create-user form breaks.

That arrangement immediately found a real bug. A method-level fallback runs
*inside* the nested router, where axum has already stripped the prefix it
matched, so the proxy read `req.uri()` and forwarded `/users/7` for a request
to `/api/users/7`. Python matched the SPA's GET-only catch-all instead and
answered 405 where it alone answers 404. `OriginalUri` is the untouched URI and
is what the proxy reads now; the top-level fallback had only ever worked
because nothing had stripped anything by the time it ran.

### The auth router

Ten endpoints, and the ones carrying contracts are `login` (C1 bcrypt, C2
constant-time miss, C9 rate limit, C7 cookies), `logout` (C27), and the 2FA
routes (C3 Fernet at rest, C6 pyotp compatibility).

Two details look like inefficiencies until you see what they defend.

**A login for a user that does not exist still pays for a bcrypt verify.**
Returning early would make "no such user" measurably faster than "wrong
password", and that difference is a username oracle: an attacker learns which
accounts exist without ever guessing a password.

**The username rate-limit key is never locked out, only rate-limited.** The IP
key gets both counters; the username key gets the short window and no lockout.
Reversing that would let anyone who knows an admin's username lock that admin
out of their own panel from a botnet. The live Redis keys show the asymmetry
directly - after a run of failed logins there is a `failures:127.0.0.1` key
and no `failures:user:admin`.

The Redis key names are Python's, byte for byte, and that is not tidiness:
while the strangler is in place a login can be served by either side, and a
second set of counters under different names would mean eight attempts through
Rust *plus* eight through Python. The window would silently double.

### Three bugs that only deploying could find

Each of these passed every test and every comparison that did not involve
running the thing in its real place.

**`NoNewPrivileges=true` blocks `sudo` outright.** Hardening the new service
unit looked obviously right. Every ordinary page kept working and every
privileged one failed with "the no new privileges flag is set" - a firewall
page that renders and does nothing. `snpanel-api.service` has carried
`NoNewPrivileges=false` with a comment saying exactly this since it was
written; the new unit was not read against the old one.

**`RestrictAddressFamilies` without `AF_NETLINK` is worse than that.** With
sudo working, the helper ran, exited 0, and reported `Chain active: no` with
blank set counters - `nft` talks to the kernel over a netlink socket and could
not open one. No error anywhere: a firewall page quietly saying "off" about a
firewall that is on. The shadow diff caught it as two differing strings, which
is the only reason it was noticed.

**The `Secure` cookie flag**, below, which needed the process to be holding the
certificate itself.

The units now live in `installer/files/` with those reasons in comments beside
the directives, and `api-browser-check.sh` asserts `Chain active: yes` so the
netlink one cannot come back silently.

### The `Secure` flag, found by deploying rather than by testing

Python decides whether to mark the session and CSRF cookies `Secure` by asking
two questions: is there an `X-Forwarded-Proto: https`, **or** is this request's
own scheme https. The Rust port asked only the first, which was invisible for
as long as it ran behind something else - and wrong the moment it held the
certificate itself. A real login over real HTTPS returned cookies with no
`Secure` flag, which a browser will happily send over plain HTTP.

The fix is to carry "this process terminates TLS" in the application state,
because a server-side request URI in Rust has no scheme to consult. The lesson
is narrower than "test more": this class of bug cannot be found by comparing
two implementations that are both behind a proxy. It needed the deployment.

### What the shadow diff compares

Status and body. Body as JSON with keys ordered, because key order carries no
meaning and reporting it would bury the differences that do.

Headers are **not** compared, and this document previously said they were.
That was wrong, and worth correcting rather than quietly fixing: the `Secure`
bug above lived in a header and the diff would not have caught it. Comparing
`Set-Cookie` is not straightforward while the two sides are reached over
different schemes - the Rust side over HTTPS and the Python side over
loopback HTTP - so the flags legitimately differ during a diff run. The
browser-flow script checks them instead, against the public endpoint, where
there is only one right answer.

Some values *cannot* match: a CPU percentage or a free-memory figure read
microseconds apart differs no matter how correct both sides are. Those are
declared volatile and compared structurally - same key, same type - rather
than by value. Being allowed to vary is not being allowed to change shape, so
a volatile field whose type differs is still a difference.

A **per-case** volatile list was added alongside the global one. The global
list is a claim about a field wherever it appears; a case volatile is a claim
about one endpoint. `apt-get update` lists its mirrors in whatever order they
answer, so `updates-os-auto` disagrees with itself between two calls - while
`stdout` on the firewall endpoints is exactly what has to be compared. Three
tests hold the line: a case volatile silences that field and no other, and
still reports a type change or a missing field.

The comparison set includes the **refusals**, not just the successes: a port
that accepts what the original refused is a security regression, and it would
pass a test that only checked the happy paths. It also includes the
**validation errors**, which is how four real differences were found: FastAPI's
422 entries carry an `input` field; Pydantic reports *every* missing field
rather than the first; `ctx.error` on a value error holds the exception object,
which renders as `{}`; and `SystemAutoUpdateConfig` gives every field a default,
so reading the service's guard instead of the schema made a working button
answer 422.

### C3 is proved on production ciphertext, not on a fixture

The phpMyAdmin hand-off is the one ordinary request that decrypts a stored
customer database password, so `api-shadow-check.sh` mints one through Rust and
consumes it through Python, then mints through Python and consumes through
Rust, and compares the passwords that come out. They agree - on the ciphertext
the installed panel actually holds.

That is risk R1 in the plan, the one that silently destroys every customer's
database password if the key derivation is off by a byte, and it is now closed
against real data rather than against a file this repository generated.

### One endpoint that mutates what it reports

`/api/updates/status` refreshes a stale release check into a state file both
implementations share - and the helper's own output is a snapshot of that same
file. Called cold, whichever side goes first rewrites what the second sees. The
check script warms the cache first; both then find it fresh, neither writes,
and the snapshots agree. Recorded because it looked exactly like a port bug.

### Why the database crate asserts rather than assumes

Two processes writing one SQLite file need WAL, or the second writer gets
`SQLITE_BUSY` immediately. `journal_mode=WAL` in the connect options is a
*request*, and on a database another process already holds open in a different
mode it can be refused. `Database::connect` reads `PRAGMA journal_mode` back
and refuses to start if it is not WAL - finding that out at startup is far
better than finding it out as intermittent failures under load.

It also refuses to create a missing database. An empty database appearing
where the panel's should be looks like total data loss to whoever finds it.

### The auth middleware is a transcription, not an interpretation

`_user_from_token` does six things in order and so does this: decode with
HS256; `sub` is the **username**; look the user up; refuse an inactive user
*unless* the `imp` claim is set; compare the user's `token_version` to the
token's `tv`; refuse a `jti` in `revoked_tokens`. Then, separately, CSRF: a
cookie-authenticated mutating request needs `snpanel_csrf` to equal the
`X-CSRF-Token` header, compared in constant time because a byte-by-byte
early return leaks the cookie through response timing.

Bearer auth is exempt from CSRF, deliberately: a browser will not attach an
`Authorization` header cross-origin on its own, so there is nothing to forge.

### 61 ported, 60 reachable

Worth stating separately, because the two numbers are not the same and the
difference was invisible until a real website was created through the panel.

`ops::dispatch` handles 61 operations. The panel uses the **CLI** transport,
and for a while only 49 of those had a CLI arm - the other twelve were
implemented, tested, and unreachable, so the panel silently got the bash
version. Creating one website exercised four of them (`site-file-write`,
`nginx-custom-write`, `waf-site-save`, `certbot-issue`) and the audit trail
showed them being delegated.

All but one are now reachable. `nginx-write-site` has no bash counterpart
because the Python writes the vhost itself - see IMPROVEMENTS.md I4b - so it is
socket-only by design rather than by omission.

Two things had to be fixed rather than merely wired:

- **`php-config-write` was the wrong operation.** I had built it as "generate
  an ini from five fields". The bash reads a **whole ini from stdin**, validates
  it against a **seven-directive allowlist**, installs it as `99-snpanel.ini`
  and *restarts* PHP-FPM. The allowlist is the security boundary: without it,
  whoever reaches the PHP config page can set `extension=`,
  `disable_functions`, `open_basedir` or `auto_prepend_file` as root for every
  site on the box. Reimplemented faithfully, including the 8 KiB limit, the
  rejection of carriage returns, and - deliberately - the rejection of comment
  lines, which the bash also refuses because it skips only empty ones.
- **`certbot-issue` had `email` as mandatory.** The bash allows issuing
  without one and falls back to `--register-unsafely-without-email`, so a
  mandatory field would have refused a request the bash accepts.

The `<site-user> <site-root> <path>` form the bash uses for site operations
collapses into one `SitePath` in the CLI arm, and the three arguments are
checked against each other first: a root that does not belong to the named
user is refused rather than one of the two being silently believed.

### The cutover

`/usr/local/sbin/snpanel-helper` is now the Rust binary. The bash helper was
moved aside to `snpanel-helper.sh`, and the Rust one `exec`s it for any
operation not yet ported. Nothing about the panel changed: same path, same
sudoers rule, same call from `shell.privileged()`.

That fallback is what makes the milestone reachable now rather than after the
last of 111 subcommands. `exec` rather than spawn-and-wait, for three reasons
that each matter:

- the environment carries through, including `SUDO_USER`, which the bash helper
  checks as its own authorisation - verified by calling it directly as root and
  watching the bash guard still refuse;
- stdin, stdout and stderr are the same descriptors, so an operation that reads
  a password or a crontab from stdin still works;
- the exit status is the bash helper's own.

The procedure is committed as `installer/files/helper-cutover.sh`, with a
one-command rollback. It refuses a second run - a second cutover would move the
Rust binary aside as though it were the bash one and turn the fallback into a
loop.

#### What the cutover was verified against

Nineteen checks through the panel's own path (`sudo -u snpanel sudo -n
/usr/local/sbin/snpanel-helper ...`):

- a ported operation is answered by Rust, confirmed by its audit line rather
  than assumed;
- an unported one is delegated, and the bash helper produces the real error;
- the bash guard still refuses a caller that is not `snpanel`, through `exec`;
- stdin survives delegation - a crontab written and read back;
- the allowlist still refuses `sshd` and still refuses stopping `snpanel-api`;
- `admin` logs in, and `/api/services/list`, `/api/firewall/status`,
  `/api/websites` and `/api/waf/status` all return 200;
- `/api/firewall/status` reports the rule the Rust helper had just written -
  the panel and the helper agreeing end to end.

Then a real website, created through the panel API:

- the site tree landed with the right owner and mode, `/home` still 0711 (C33);
- the vhost was written, `nginx -t` passed, nginx stayed up;
- `site-runtime-ensure` - **not** ported - was delegated to bash, which created
  the PHP-FPM pool and reloaded it;
- a PHP page then served `php-via-rust-helper:8.4.25` through that pool;
- the website deleted cleanly and the panel stayed healthy.

And the cutover script itself: refuses a second run, rolls back to bash with the
panel still answering 200, and rolls forward to Rust again.

#### Three test bugs found along the way

Recorded because each produced a confident wrong answer:

- The site-root check guessed a `bp_<domain>` username. A site owned by the
  admin panel user lives under *that* user's home, so it looked for a directory
  that was never going to exist.
- The PHP check looked for the FPM socket immediately after creation.
  `systemctl reload php8.4-fpm` returns before the new pool's socket appears,
  so the test was reporting its own impatience as a failure.
- A diagnostic ran after the test's own cleanup and concluded the vhost had
  never been written.

None was a defect in the panel or the helper. All three were fixed rather than
worked around, because a test that fails for the wrong reason will one day pass
for the wrong reason too - which happened here as well, in the SIGPIPE case
below.

### The nftables merge bug

Worth recording because it was invisible in unit tests and obvious the moment
the helper drove a real kernel.

`nft -f` **merges** into an existing table; it does not replace it. So every
`firewall-apply` appended another `jump snpanel_input` to the base chain and
re-added every rule. After eight applies the running box had eight jumps, and
`firewall-disable` did nothing at all, because the base chain from the previous
apply survived the load that was supposed to remove it.

The fix is the standard nft idiom, all in one `-f` file so the load stays a
single transaction:

```nft
table inet snpanel {}        # so the delete cannot fail on a fresh box
delete table inet snpanel
table inet snpanel { ... }   # the real ruleset
```

Verified on the container: five consecutive applies now leave exactly one jump,
one chain and one copy of each rule; disable removes the hook and keeps the
chain (C39); enable restores it; and the panel answered 200 throughout.

### A test that passed for the wrong reason

While confirming the fix, the shell check `nft list … | grep -q "hook input"`
reported the hook as absent when it was present. `grep -q` exits on the first
match, `nft` dies of SIGPIPE, and under `set -o pipefail` the pipeline reports
failure even though the match succeeded. The check read as a pass. Every such
check now reads the ruleset into a variable and matches that instead - a false
pass on a security-relevant assertion is worse than a false failure.

### Why `SO_PEERCRED` is not a cosmetic change

The bash guard is `[[ "${SUDO_USER:-}" != "snpanel" ]]`. That trusts an
environment variable. It is sound in practice only because sudo sets it and the
sudoers file is narrow — the helper itself cannot tell a real sudo invocation
from a process that already had root and exported `SUDO_USER=snpanel`.

`SO_PEERCRED` is answered by the kernel about the process on the other end of
the socket. It cannot be set, spoofed or inherited. Proven rather than asserted:
in the container, with the socket deliberately loosened to mode 0666 so the
permission bits could not be the thing doing the work, a connection from
`nobody` came back

```
{"ok":false,"error":{"kind":"not-authorised",
 "message":"caller uid 65534 is not the panel user (uid 999)"}}
```

and the journal recorded `peer_uid=65534 peer_pid=61120`.

### One bug found while writing the tests

The first socket test simulated systemd activation by setting `LISTEN_PID`
inside `Command::pre_exec`. `std::env::set_var` is not async-signal-safe, so
after `fork` it deadlocked on the environment lock and the suite hung until it
was killed. Replaced with a `SNPANEL_HELPER_SOCKET` override, which is also
useful on its own — an operator can run a second helper on a scratch path
without disturbing the live one. The systemd path is covered in the container,
where systemd itself passes the fd.

### `\S` is not `is_ascii_whitespace`

The access-log pattern was ported by hand, like every other pattern here,
because `regex` is deliberately not in the lock file. Two of its whitespace
decisions were wrong, and neither showed up until a mutation run asked for a
corpus line that reached them.

Python's `\s` is `Py_UNICODE_ISSPACE`. It covers the vertical tab, the four
separator controls at `\x1c`-`\x1f` and the non-breaking space — none of
which `u8::is_ascii_whitespace` knows, and two of which `char::is_whitespace`
does not know either. So:

- A line whose address was followed by one of them **parsed here and was
  refused there.** The pattern wants a literal space after `\S+`; with the
  ASCII predicate the scanner swallowed the separator into the address and
  found its space one field later. The two implementations disagreed about
  whether a request had happened at all.
- `_split_request` uses `str.split()`, which is the same predicate.
  `split_whitespace` would have kept `\x1f` inside a word, putting the path
  in the method column.

Both now go through the generated `pyunicode` tables — the same ones the
username and password rules use — and the corpus carries a line for each.
The fix is small; what it cost was a reminder that "whitespace" is three
different sets depending on who is asking.

Two more branches were only found by breaking them: `body_bytes` is `\S+`
and required, but every corpus line that omitted it also omitted the space
before it, so an earlier check refused them first — only a *double* space
after the status reaches that rule. And the two-word request arm
upper-cases its method, but the corpus's only lowercase method was in a
three-word request. Two survivors, two lines, both closed.

One mutation was deliberately deleted rather than made to fail: the search
haystack joins `status` as a number, and every raw line already carries its
own status, so no search can tell the formatted number from the raw text.
The arm stays because the Python joins the same thirteen fields. A test that
cannot fail is not evidence, and pretending otherwise inflates the count.

### A body `bool` is not only `true` and `false`

Found while porting the PHP tuner, and it was not the tuner's bug. FastAPI
validates a request body in pydantic's **lax** mode, so `"true"`, `"on"`,
`"yes"`, `"y"`, `"t"`, `1` and `1.0` are all booleans. Seven call sites here
read `Value::Bool` and refused everything else with a 422 — so a client
sending `{"enabled": "true"}` got a refusal from Rust and a 200 from Python.

And it was wrong in the other direction too. For a plain `bool` field with a
default, pydantic **refuses** an explicit `null`; two of those call sites
treated `null` as "take the default". Only `Optional[bool] = None` accepts
it, which is what `packages` and `users` have and why those two keep
skipping it.

The refusals are not one error either: a value of the right kind that
cannot be read is `bool_parsing` (`2`, `"01"`, `" true"` — there is no
trimming), and a value of the wrong kind is `bool_type` (`null`, a list, a
float that is not 0 or 1). The panel shows the message.

All of it is now `errors::read_bool`, measured against the installed
pydantic over 43 values. One existing test had to be **inverted**: it
asserted that `{"terminal_enabled": "yes"}` was refused, which is what made
the port confident. A test written from the same misreading as the code
does not catch the code.

### The PHP tuner

`maintenance`'s four `php-tune` endpoints. Most of the module is arithmetic
over one number — how much RAM the box has — and string comparison deciding
whether a row is offered as a change, so all of it is corpus-measured: 39
memory sizes at every tier boundary and floor crossing, 56 spellings of a
setting, 34 recommendation lists, 24 ini files, 21 version strings and six
whole plans.

The reason strings are compared byte for byte. They are what an
administrator reads before pressing the button, so a port that reworded
them would change the product, and a corpus is the only way to be sure a
transcription of fourteen Vietnamese sentences is exact.

Three behaviours that a reading of the code would get wrong, and the corpus
pins each:

- **A bare number keeps its digits as written.** `_normalise` returns the
  matched *text* for a unitless value, not the parsed integer, so `007`
  normalises to `007` and compares unequal to `7`.
- **A pool file's name and its numbers can come from different sections.**
  The first `[name]` header names the pool; the last assignment of a key
  sets its value.
- **`supports_jit("8")` is false.** The comparison is between tuples, and
  `(8,)` is less than `(8, 0)`.

Two more of Python's string rules went into `pyunicode` for it.
`str.splitlines()` breaks on eleven things where `str::lines` breaks on
three — an ini file with a form feed in it is two settings there and one
line here, and a reader that splits `key = value` at the wrong place does
not fail, it reports a different setting. And `str.strip()` is the same
whitespace predicate as `\S`, not Rust's `White_Space`. Both are replayed
against CPython over 89 and 27 cases.

### The first job registry, and the archive checks behind it

`POST /files/extract` and the two endpoints that watch it, moved together
because the registry they share is process-local — see the plan for why
that makes them one chunk rather than a blocker.

The checks are the point. Every one of them stands between a customer's
upload and the rest of a shared machine, and the corpus is built from real
archives carried base64 so the Rust reader sees the same bytes rather than a
description of them: 23 zips, 10 tars, 5 destinations that already hold
something, and 29 member names.

Three behaviours that a reading of the Python would not give you:

- **A zip entry has three ways to be a directory.** A trailing slash, or
  directory mode bits with a zero size, or being the implied parent of
  another member — and each of the three is the only one that fires for
  some archiver's output. `zip` on Linux writes directory entries without
  the slash.
- **The implied-parent test needs the zero size.** A non-empty file called
  `d` in an archive that also holds `d/x.txt` stays a file.
- **Overwriting a symlink is refused as "Archive contains unsafe paths"**,
  not as "Refusing to overwrite a symlink". Resolving the target follows
  the link out of the tree, so the earlier check fires first. A port that
  produced the later message would still be safe and would still be a
  different answer on the customer's screen.

And one the tar side does not share with the zip side: tar can carry a hard
link, a FIFO and a device node, and **all** of them are refused, not only
symlinks. A device node unpacked into a customer's tree with the helper's
privileges is a hole nothing else here would catch.

54 mutations, all caught — but it took five runs, and two of the reasons
are worth writing down.

**The tar test was proving its own reader.** It classified each member
itself with a copy of the production logic, so breaking `read_tar_entries`
— the function that actually decides whether a device node reaches the scan
— changed nothing it could see. Three mutations survived on that alone. The
test now reads the archive the way the handler does.

**And one run was invalidated by interference.** A mutation runner holds a
snapshot of the files it edits and restores them at the end; editing the
tree while it runs, or starting a second one, produces results that are
noise. That happened here and left `file_jobs.rs` sitting in a mutated
state that the test suite still passed — because the mutation was the one
whose test had not been written yet. The rule is simple and was broken
anyway: confirm no runner is alive before touching anything.

Two other things the port had to reproduce rather than improve. The
registry evicts the oldest **finished** jobs and never a running or queued
one, so a busy box exceeds fifty entries rather than forgetting what it is
doing. And the work is limited to two at a time, which on a shared machine
is the ceiling on how much disk an extraction storm can move at once — an
unbounded `tokio::spawn` would have been the obvious port and the wrong one.

One porting bug found while writing it: `sorted(..., reverse=True)` does
**not** reverse ties, and a Python dict is ordered, so two jobs created in
the same second come back in the order they were queued. A `HashMap` gives
neither, and the stamp has one-second resolution, so the two cards would
have swapped places between one poll and the next.

### Two more file-manager endpoints, and a function that was already here

`POST /files/archive` and `DELETE /files/{website_id}`.

The first thing this batch turned up is that it did not need a new
function. `files.rs` has carried `clean_relative_path` since the
file-manager reads landed, marked dead with a comment saying its callers
are "the upload and archive endpoints, which are a later batch" — and the
archive batch wrote a second copy of it anyway. Two transcriptions of one
Python function drift, and the one that drifts is the one nobody is
looking at. There is one now, and the `dead_code` allowance is gone.

Two behaviours the corpus settled that a reading would not:

- **The archive's extension is added, not replaced.** A customer who types
  `backup.tar.gz` and picks zip gets `backup.tar.gz.zip`. The *name* is
  matched case-insensitively, so `BACKUP.ZIP` keeps its own spelling; the
  *format* is matched exactly, so `ZIP` is refused. And the name is
  validated before the format, so `..` in a bad format reports the name.
- **`_archive_arcname(base, base)` is `"."`, not `""`.**
  `str(Path("a").relative_to("a"))` is a single dot, so the "Cannot archive
  the current folder into itself" message the Python carries is
  unreachable. The port returned an error there until the corpus said
  otherwise. Selecting the current folder *is* refused, a few lines later,
  where the output turns out to be inside a selected folder.

`_run_as_site_user` takes a working directory and the port had it fixed at
the site root, because every caller so far passed that. This is the first
that does not: `zip -r name -- items` has to run **inside** the folder
being archived, or the names inside the archive come out relative to the
root.

65 mutations, all caught. Two anchors were stale before the run — one
because `rustfmt` had reflowed a match arm, one because the text appeared
twice — and each would have been reported an hour later, beside results
that were fine. Every runner now checks all its anchors before the first
build, which turns that hour into a second.

### One environment limitation, again

MariaDB's postinst could not create its system tables, exactly as it could not

of the panel, and it happens on a real host to neither.

### Three things that only reading caught

None of these would have announced themselves as a platform problem:

* The panel's tools vhost declares `listen 80 default_server`. EL ships its own
  `server { listen 80 default_server; ... }` **inside nginx.conf**, where Debian
  ships it as a separate file the installer deletes. Two of them make nginx
  refuse to start. The distribution's block is commented out, not cut, so an
  administrator can see what was there.
* `/etc/phpMyAdmin` is `root:apache` mode 0750. nginx cannot read it, and the
  failure is a blank 500 with nothing in phpMyAdmin's own log.
* EPEL's `/etc/nginx/default.d/phpMyAdmin.conf` contains `fastcgi_pass php-fpm;`

### The PHP compatibility shim, and what it does not cover

The panel's Python service layer is pathed to Debian's layout: it reads and
writes `/etc/php/<version>/fpm/{php.ini,conf.d,pool.d,php-fpm.conf}` and
restarts `php<version>-fpm`. Rather than thread an OS abstraction through forty
call sites, EL presents those names as symlinks into the Remi tree, plus a
systemd alias so `php8.4-fpm` reaches `php84-php-fpm`.

This is a compatibility shim, not a port, and the difference matters:

* Remi shares one `php.d` between the CLI and FPM SAPIs, so a value the panel
  sets for FPM also reaches CLI. Debian keeps the two separate.
* Installing an *additional* PHP version from the panel refuses on EL, with the
  reason. Doing the package-name half without the shim half is worse than
  refusing: the packages install, the panel lists the version, and every tuning
  action against it fails on a path that does not exist.
* `configure_unattended_upgrades` refuses too. EL's nearest equivalent is
  dnf-automatic, configured nothing like it, and half-applying a policy the
  panel then displays as active is the wrong kind of working.

`run_os_update_now` does dispatch — `dnf -y upgrade` — because that one has a
faithful translation.

### Three real bugs, none of them about AlmaLinux

The port surfaced both. Both would bite a Ubuntu box too, which is why neither
fix lives in an EL branch.

**1. A vhost that names a directive nginx does not have.** The panel wrote
`modsecurity on;` into every vhost whose site had the WAF enabled — the default.
Without the module, nginx rejects *the entire configuration*, so the blast
radius is the machine: the next reload anywhere takes every site down with it.
Ubuntu is exposed the moment the WAF package fails to install, which
`install.sh` treats as a warning and continues past. The gate now sits where the
directives are written, and asks nginx rather than the distribution.

**2. `IFS=$'\t' read` cannot parse the firewall's own rules file.** Tab is IFS
*whitespace* in bash: runs of tabs collapse into a single delimiter, so an empty
field in the middle of a row shifts every field after it one place left. The
rules file has empty fields by design — "open port 8080 to every source" is
stored with no IP — so `3⇥allow⇥⇥8080⇥tcp` was read as `ip=8080, port=tcp`.

Two consequences, neither loud:

* `firewall_sync_sets` built the ipset entry `8080,:tcp`, ipset rejected it, and
  `deny` aborted the whole sync — `firewall-enable` failed and applied nothing.
* The branch that opens a port for everyone tests `-z "$ip"`, which after the
  shift is never true, so **the port stayed closed while the panel listed the
  rule as active**.

Ubuntu had not surfaced it because the only port-only rules the installer adds
are the SSH ports, and `firewall_add_rule` returns early for protected ports
without writing a row. Any port a user opens from the Firewall page has this
shape.

Fixed by re-delimiting through a character that is not IFS whitespace, in all
three readers of that file. Proved on both platforms: on AlmaLinux, 6 of 6
checks including `--dport 8080 -j RETURN` reaching the chain; on Ubuntu, a port
opened through the helper, applied, and removed again. Seven regression tests
cover it, one of which deliberately demonstrates the old idiom still being
broken, so nobody reinstates the shorter spelling.

**3. Turning the OWASP rule set on reported a package manager error.** Found by
the user, from the panel, on the AlmaLinux install:

```
Error: Unable to find a match: modsecurity-crs
snpanel-helper: could not install modsecurity-crs
```

True about dnf, useless about the server. This was a hole left in this port
rather than an old bug: `install_engine` already refused with the reason, and
its docstring says in as many words that handing dnf a name it will reject
"reads like a transient repository problem rather than a settled fact about the
distribution" — and then the CRS path was left doing exactly that.

The condition to test is whether nginx has the module, not which distribution
this is, so `waf_engine_present` asks nginx and both the rule-set install and
the mode switch consult it. Turning CRS *off* stays unguarded: that is the way
out of a bad state, and refusing it would be the wrong kind of strict. The
panel's `/api/waf/crs` now reports `engine_available`, so the page can show the
control as unavailable instead of offering an action that cannot succeed, and
switching it on answers 400 with the reason rather than relaying dnf.

Verified on both: AlmaLinux refuses with the explanation and still disables
cleanly; Ubuntu, which has the module, enables and disables exactly as before.

#### And one I wrote and the existing suite caught

The first version of `waf_engine_present` was `nginx -V 2>&1 | grep -qi
modsecurity`. Under the helper's `set -o pipefail` that is a false negative
generator: `grep -q` exits the moment it matches, `nginx -V` dies of SIGPIPE,
and that status becomes the pipeline's — so a *successful* match reports
failure. It would have blocked CRS on Ubuntu, where it works.

`test_the_helper_never_pipes_into_a_grep_that_exits_early` failed on it
immediately. That test exists because the same trap had been hit before, which
is the argument for writing the test that outlaws a pattern rather than the one
that checks a case.

#### Two assertions of mine that were wrong

Both were in the test, not in the code, and both are the same mistake —
asserting a shape rather than reading what the layer below actually promises.

The renderer emits a host address **bare** (`203.0.113.44`), not
`203.0.113.44/32`, while keeping the prefix on a network. That is what nftables
wants: in an `ipv4_addr` set with `flags interval` a full-length prefix is
redundant, and `nft list` prints it bare whichever form was loaded. I asserted
the `/32` and called its absence a C13 failure.

C13 is a property of the **write** path: the helper normalises a bare address to
`/32` as it writes `rules.tsv`. That run hand-wrote the file, so there was
nothing to normalise, and `firewall status` correctly showed what the file said.
A reader that silently rewrote its input would be the actual bug — that is how
you lose track of what a firewall is doing.

### A working WAF on EL, built rather than packaged

The gap above is about packages, not about whether the thing can work. On the
test container the engine was built from source and the WAF now runs:

| | |
|---|---|
| libmodsecurity | 3.0.14, built with PCRE2, libxml2 and curl |
| the nginx connector | `ngx_http_modsecurity_module.so`, 203 KB |
| OWASP CRS | 4.10.0, 25 rule files |

It works, and "works" here means requests are stopped, not that the module
loads: `/.env`, `/wp-config.php`, the PHPUnit `eval-stdin.php` probe and the
Laravel Ignition RCE probe all answer 403, while an ordinary request and a
query that merely *mentions* `environment` still answer 200. Enabling the OWASP
rule set through the panel, the action that started this, answers 200.

This is deliberately **not** in the installer. A dynamic module is built against
one nginx, and when `dnf` upgrades nginx to another, nginx does not lose the WAF
- it refuses to start, and every site on the machine goes with it, during an
unattended package update.

So the trial ships with a guard: an `ExecStartPre` on nginx that runs before
nginx's own `-t`, and, if the configuration is broken *and* the breakage names
the module, moves the load directive aside and logs loudly. Degraded beats down.
It was tested by corrupting the module on purpose: nginx started, the site kept
serving, the panel reported the engine as gone, and everything came back when
the module was restored. 11 of 11.

Two further caveats before this could be an installer step:

* The build uses EL10's default `-march=x86-64-v3`. The module will not run on
  an older CPU, so it has to be built on the target rather than shipped as a
  binary.
* The guard disables a stale module; it does not rebuild it. Shipping this
  properly means rebuilding on nginx upgrade, which is a dnf hook and more
  machinery than a trial needs.

#### Three copies of one question, and how each was wrong

"Is the ModSecurity module loaded" is asked by the panel, by the privileged
helper and by the post-install check, and each got it wrong in turn:

1. Both originally asked only whether Debian's packaged module file existed and
   whether `nginx -V` mentioned modsecurity. A module built from source is in
   neither: `-V` reports what nginx was *compiled* with, not what it loaded. So
   the module loaded fine and the panel went on refusing CRS.
2. The replacement used `nginx -T`, which does report loaded modules - and dies
   before printing anything when run as the unprivileged `snpanel` user, which
   is exactly who asks. It returned False precisely where it was needed.
3. The version that reads the configuration files used `grep -r` over the
   module directories. nginx includes `*.conf` and nothing else, and the guard
   above *renames* a broken module's file rather than deleting it - so a
   recursive search reported a disabled module as present. That is the worst
   failure of the three: no protection, and a panel claiming there is some.

The answer that survived is the one nginx itself uses: read `nginx.conf` and the
`*.conf` globs it includes. All three implementations now use it, and
`test_crs_needs_an_engine.py` pins them to each other - including the disabled
-module case, which is the one only the guard test found.

### Five things 26.04 broke, and what each one really was

Only one of them was about Ubuntu 26.04 as such. The rest were assumptions that
had never been tested anywhere else.

**1. Ondrej's PPA has no `resolute` suite.** Checked against the PPA itself:
the newest is `noble`. `PHP_VERSIONS="8.3 8.4"` was a constant at the top of
the installer, so on 26.04 it would add an empty repository and then fail on
every package name. The versions now come from the platform table, and an
operator who names them explicitly still wins.

**2. Python 3.13 removed the `crypt` module**, and 26.04 ships 3.14. The panel
already caught the ImportError, so nothing crashed — which is what made this
the most dangerous of the five. `verify_shadow_password` simply returned False
for every input, so every account whose stored hash came from another panel was
locked out with "incorrect password", with no traceback and no log line. A
fresh install is unaffected, because the admin's hash is bcrypt.

passlib, already a dependency, can do `$6$` but not `$y$` yescrypt — which is
what Debian 12 and Ubuntu 24.04+ actually write into /etc/shadow — so it could
not stand in. `legacycrypt` binds the system libcrypt through ctypes and was
verified end to end: a user row carrying a real yescrypt hash logs in (200) and
a wrong password is still refused (401), on Python 3.14.

**3. `libmodsecurity3` became `libmodsecurity3t64`** in the 64-bit time_t
transition. The installer named it explicitly; it is a dependency of the nginx
module, so the module alone is both correct and version-proof.

**4. sudo 1.9.17 removed `requiretty`.** Ubuntu 26.04's build rejects the whole
sudoers file over the negation and the install stops. AlmaLinux 10 ships *the
same version*, 1.9.17p2, and parses it without complaint — so this is a
difference between builds, not versions, and branching on the distribution
would have been wrong. The installer asks visudo instead: it hands the parser a
file that uses the setting and keeps the line only if it is understood. The
line is not simply deleted because RHEL once enabled `requiretty` globally and
the helper runs with no TTY.

**5. SQLAlchemy 2.0.30 predates `__firstlineno__`**, the class attribute Python
3.13 introduced, and raises `Can't replace canonical symbol` on import. Of the
eighteen pinned dependencies this was the only one that failed on 3.14 —
alembic only failed because it imports SQLAlchemy. Bumped to 2.0.54, the newest
in the same series, and the suite re-run on 3.12 to check nothing regressed.

### A sixth, found from the panel: adding a repository that does not exist

Reported after the install, from the panel's "install PHP version":

```
E: The repository '.../ondrej/php/ubuntu resolute Release' does not have a
   Release file.
snpanel-helper: PHP FPM config directory not found: /etc/php/8.4/fpm/conf.d
```

This is the same fact as item 1 above - the PPA does not publish `resolute` -
reaching the machine through a second door. `install.sh` was taught to ask
`PHP_FROM_PPA` before adding the repository; the privileged helper, which is
what the panel button actually runs, was not taught anything and added it
unconditionally.

The failure was not the interesting part. `add-apt-repository` *succeeds* for a
suite the PPA does not have: it writes the source file, and from then on every
`apt-get update` on the machine fails - including the ones the installer and
the updater run themselves. The damage outlived the action that caused it, and
a user who tried once would have a subtly broken box afterwards.

The helper now asks the PPA over the network whether it publishes this release
*before* adding anything, and refuses with the versions that are installable if
it does not. A second, smaller bug in the same lines: the "is the PPA already
configured" check read only `*.list`, while `add-apt-repository` writes deb822
`.sources` on current Ubuntu - so it never saw its own work and would have
re-added the repository on every attempt.

### And what that refusal got wrong, which was worse

The first version of the refusal named the installable versions as "7.4 8.5".
There is no PHP 7.4 on Ubuntu 26.04. The check was `apt-cache show`, which is
the obvious idiom for "does this package exist" and answers a different
question - measured:

```
php7.4-fpm    apt-cache show -> rc=0    apt-cache policy -> Candidate: (none)
```

Something in the archive still references the name, so `show` finds a record
with no installable version behind it.

That idiom was not only in the message. It was `pkg_exists` in
`installer/platform.sh`, which is how the installer decides which PHP extension
packages to hand to apt - and a false yes there puts an uninstallable name into
a single `apt-get install`, failing the whole transaction instead of skipping
the one optional module the check exists to skip. It was also the gate deciding
whether to add the PPA at all, and the loop selecting extensions in the helper.

All four now ask `apt-cache policy` for a candidate, and a test asserts both
implementations read it the same way: an extension the installer believes in
and the panel does not, or the reverse, is a disagreement nobody would think to
look for.

The dnf branch was deliberately left alone. It was not re-measured, because the
AlmaLinux container had already been deleted, and changing an idiom on a
platform that cannot be tested right now is worse than keeping one that has
worked.

### One more copy of the same mistake

`platform-check.sh` hardcoded `8.3 8.4` and a default of `8.4`, so it reported a
correctly installed 26.04 as having no PHP. It now discovers the versions from
`/etc/php/<version>/fpm` instead. That is the fourth time in this port a check
has been written against one platform's answer rather than against the question.

### Two more bugs, from doing it

**`CREATE USER IF NOT EXISTS` is not idempotent in the way the installer needed.**
`setup_panel_user` generates a fresh MariaDB password, creates the account with
`IF NOT EXISTS`, and writes that password into `~snpanel/.my.cnf`. On a second
run the account already exists, so the statement does nothing - including
nothing to the password - while the file is overwritten. From then on:

```
ERROR 1045 (28000): Access denied for user 'snpanel'@'localhost'
```

and every database page answers "MariaDB error: Command failed". Nothing about
this is specific to 26.04; it bites any re-run on any platform, and a user
whose first install failed halfway is in exactly that position. It surfaced
here because this install needed three attempts. Fixed with `ALTER USER` after
the create, and the installer now checks that the panel can authenticate with
what it just wrote rather than discovering it later as a 500.

**The Rust CLI named one panel unit; after the cutover there are two.**
`status`, `logs` and `restart` all hardcoded `snpanel-api`, which is stopped on
purpose once the front door is in place. `status` reported a serving panel as
inactive and `logs` read an empty journal, but `restart` was the one that
mattered: it restarted the stopped unit, left the running panel untouched, and
printed "Done." An operator restarting to clear a problem would have been told
it had happened when it had not. The units are now discovered, and a check
confirms the *process identifiers actually change* rather than trusting the
output.

### Auto tune asked for a PHP version the machine did not have

Reported from the panel:

```
snpanel-helper: PHP FPM config directory not found: /etc/php/8.4/fpm/conf.d
```

Ubuntu 26.04 carries PHP 8.5 and nothing else. Four separate places held "8.4"
as a constant - the `php-config` and `php-tune` query defaults,
`settings.default_php_version`, and the interface's initial React state - and
the installer, the one thing that knows which version it just installed,
recorded it nowhere.

The check that should have caught it was looking at the wrong set:
`SUPPORTED_PHP_VERSIONS` is what the panel knows how to *tune*, not what the
machine *has*, so a supported-but-absent version passed validation and went
straight to the privileged helper - which reported a path the operator never
chose.

Fixed in two halves, both needed:

* the panel reads the installed versions off disk and resolves against them, so
  machines installed before this change and machines where a version was later
  removed both behave;
* the installer writes `DEFAULT_PHP_VERSION`, so a fresh install does not rely
  on the fallback.

The resolver tells two cases apart, which the first version of it did not:

| asked for | outcome |
|---|---|
| nothing | the machine's default |
| a version that is installed | honoured — an operator running several versions and naming one means it |
| a supported version that is absent | the machine's default; this is the interface's stale constant arriving, not a choice |
| anything else (`9.9`) | refused — silently tuning something else would hide a mistake |

An existing test, `test_an_unknown_php_version_is_refused`, caught the first
version of the resolver swallowing `9.9`. The interface needs no change: the
response carries the version acted on, and the page uses that for its next
call, so the stale constant is corrected on the first answer.

### One that was mine, not the product's

Diagnosing the hand-off, I called the token-minting function directly as root.
`sso_tokens.py` creates `/tmp/snpanel-phpmyadmin-sso` with `mode=0o700,
exist_ok=True`, so whoever gets there first owns it - and the panel, which runs
as `snpanel`, then could not write into a root-owned directory. Every hand-off
answered 500 until the directory was removed. The design is right; the
diagnostic was not, and it is worth remembering that running a service's own
code as root can leave the service worse off than it started.

### What Ubuntu 26.04 cannot have yet

PHP 8.4, and the panel is right to say so.

Measured rather than recalled: `rpms.remirepo.net/enterprise/` publishes no
`.deb` at all - its tree is `4/ 4AS/ 4ES/ ...`, RHEL generations - so Remi
cannot serve a Debian system whatever it is pointed at. Ondrej's PPA has no
`resolute` suite, and its `devel` suite reports `Suite: noble`, so that is not
a 26.04 build either. `apt-cache policy` on the machine agrees: 8.5 has a
candidate and 8.1 through 8.4 have no entry.

So there is no apt source today that gives Ubuntu 26.04 a PHP 8.4. The helper's
refusal is accurate, and the versions the panel offers there are 8.5 alone.

The multi-version story does work, on the releases the ecosystem has caught up
with: Remi gives 8.3 and 8.4 on AlmaLinux 10, and Ondrej gives 8.3 and 8.4 on
Ubuntu 24.04. Both were installed and verified in this project. 26.04 is simply
newer than its PHP packaging.

**Ubuntu 26.04 support has been withdrawn.** The port worked and the panel ran,
but working is not the same as supportable: a panel whose whole job includes
choosing a site's PHP version cannot offer exactly one, and the one it offers -
8.5 - is newer than most application code in use. Keeping the claim would have
meant the first honest test of it happened on a customer's server.

What would bring it back is a single fact changing: Ondrej's PPA publishing a
`resolute` suite. At that point the platform table needs one entry restored and
the refusal test in `crates/snpanel-osabi/src/detect.rs` inverted, both of which
are small because the rest of the port is still here and still correct.

### Debian is not Ubuntu spelled differently

Three things had to change, and one of them would have failed the very first
package transaction:

* **`software-properties-common` is not in Debian's archive.** It was in the
  base package list because Ubuntu needs it for `add-apt-repository`. Asking
  Debian for it fails outright. The list is now per-distribution rather than
  per-family.
* **There is no PPA.** The same maintainer's packages come from
  packages.sury.org, added with a keyring and a sources list. The key is
  written to `/usr/share/keyrings` and named with `signed-by`, so it can vouch
  for that one repository: a key in `trusted.gpg.d` is trusted to sign for
  *every* repository on the machine, which is a far larger promise than "these
  PHP packages are Ondrej's". If the suite turns out to be absent the source is
  removed before the failure is reported — the lesson from the PPA that was
  added for a release that did not have one and left every later `apt-get
  update` broken.
* **NodeSource publishes no trixie suite**, so nothing is piped from a vendor.

### The contract difference the shadow diff found

One of the 89 comparisons differed, and only on this platform:

```
DIFF  GET /api/panel-settings
        panel_hostname: rust "snpanel.deb13" vs python ""
```

Python validates the host before reporting it. `DOMAIN_RE` requires a
letters-only top level, so `snpanel.deb13` is not a domain,
`normalize_panel_hostname` raises, and the panel reports an empty hostname with
the configured port. The Rust port split the URL syntactically and reported
whatever string was in it.

The test hostname is what exposed it - three earlier platforms used names with
ordinary top levels - but the gap is not about the test. **The panel offers to
request a certificate for the hostname it reports**, so the two halves
disagreeing about whether a host is usable is a difference with consequences.

Fixing it turned up a second hole in the same function: `rsplit_once(':')`
splits inside an IPv6 literal, so `http://[::1]:2222` yielded `[::1` as a host.
Python's `urlparse` reads the literal correctly and then rejects it. Both sides
now answer the same way, and for the same reason rather than by coincidence.

Five Rust tests cover it, including the IPv6 literal and a port outside
1..65535, which Python normalises and the Rust side had not.

### A race in the check, not a fault in the platform

The post-install check reported the per-site PHP-FPM socket as missing while,
in the same run, a PHP page served correctly through nginx. Both cannot be true
of the same request.

php-fpm is reloaded asynchronously after the pool file is written, so the
socket appears a second or two later; the check tested for it immediately. It
had passed on three platforms and failed on the fourth, which is what a race
does rather than evidence about the platform. The check now waits, the same way
it already waited for nginx to reload.

* The nginx ModSecurity rule engine is not packaged, and the panel says so.
